# Fixed-Hyperparameter 3-Fold Re-training of the 12 Completed Combos

Started 2026-08-11. New numbered file per this project's rule 11 (`03_tech_stack_and_rules.md`) — a large, self-contained new effort, split out rather than grown into `04_pretrained_architecture_sweep.md`.

## Why this exists

The 18-combo Optuna sweep (`scripts/train_pretrained/`) completed 12/18 combos on real Kaggle hardware (`Segmentation/scripts/train_pretrained/output/segmentation_sweep_results*/logs/*_study_summary.json`) — all 6 CNN + Hybrid architectures × 2 tissue types; all 6 Transformer combos OOM'd at `input_size=512` (root-caused via the real Kaggle traceback pulled from a Kaggle-auto-pushed notebook version — GPU memory exhausted on Trial 0's very first batch, deterministic across every trial since it doesn't depend on which hyperparameters got sampled; documented in `.project_memory/kaggle/01_kaggle_notes.md`). Fixing and re-running those 6 was explicitly ruled out ("no time left").

Each of the 12 completed combos' reported number is a **single point estimate** — one 12-trial Optuna search picked one winning hyperparameter set and trained once. The project author asked for a more robust final number: re-train each of the 12 using its own already-found best hyperparameters (no re-tuning) under K-fold cross-validation, so the thesis reports a mean ± std across independent trainings, not one lucky/unlucky draw. Longer training (`MAX_EPOCHS=250`, `EARLY_STOPPING_PATIENCE=7`) plus an LR scheduler (`trainer_engine.py` has none at all) plus a larger batch (`32`, up from `16`) were requested together, aimed at a smoother, better-converged loss curve than the original 30-epoch/no-scheduler runs.

## Scope, as actually confirmed (not the original ask)

The original ask was 5-fold × 5-repeat (25 fits/combo). Real timing evidence (measured from the actual completed Optuna runs, extrapolated per-architecture by inference-latency ratio) put that at **~125 GPU-hours worst-case across all 12 combos** — 1-4+ weeks of Kaggle sessions, incompatible with the project author's stated time constraint. This was surfaced explicitly (via `EnterPlanMode` + `AskUserQuestion`) before any code was written, rather than building the full ask and discovering the infeasibility only after the fact. **Confirmed, reduced scope:** plain 3-fold, no repeat (3 fits/combo, ~11.4h worst-case total across all 12 combos — see per-architecture table below), `BATCH_SIZE=32`. Notebook granularity went through two iterations: first **12 separate per-combo notebooks** (one per combo), then consolidated down to **3 tier notebooks** (Base/Mid/Strong, 4 combos each — the same 2 CNN+Hybrid architectures per tier as the original sweep, Transformer excluded) per the project author's explicit follow-up request, mirroring the original 18-combo sweep's own tier-notebook pattern. Each tier fits comfortably in one 12h Kaggle session (~2.3h/~3.4h/~5.7h worst-case for Base/Mid/Strong respectively).

## Design decisions and where they come from

Rather than invent this from scratch, `classification/step1_cv_harness/` was found (via a dedicated Explore-agent pass) to have already solved almost this exact problem — K-fold CV using hyperparameters already tuned by a prior Optuna sweep, with a sealed held-out test set. This effort mirrors its proven structure, with one borrowed piece from a different classification pipeline for the scheduler (the *current* classification CV harness deliberately has no scheduler, since it's a measurement-only gate mirroring its own single-run trainer exactly — this effort isn't that; it's closer in spirit to `classification/datapreparepipeline/efficientnet_b0_forniceal_5fold_cv/cv_trainer_engine.py`, the one classification pipeline that actually uses one).

- **`sklearn.model_selection.StratifiedKFold(n_splits=3, shuffle=True, random_state=42)`**, stratified on **`country` alone**, not `country x anemic_label` like classification's harness. Deliberate deviation: classification stratifies on the compound key because the anemic label *is* its prediction target; segmentation's target is a mask, so `anemic_label` is irrelevant here — only `country` matters, since it's this project's own documented confound (mask/alignment characteristics differ by country, `CLAUDE.md` §0.5).
- **Pool = `train` + `val` splits only; `test` stays completely sealed** — same `POOL_SPLITS`/`HELD_OUT_SPLIT` pattern as `classification/step1_cv_harness/cv_data.py`. Each fold's checkpoint is evaluated once, at the end, against the same never-touched test set, via `segmentation_metrics.evaluate_final_test_set()` reused completely unchanged (it already hardcodes `split="test"`).
- **Fixed hyperparameters, no re-tuning** — each combo's `learning_rate`/`weight_decay`/`loss_fn` are read directly from its real `study_summary.json` (`best_params`), dynamically discovered (glob, not hand-copied) by `train_pretrained_kfold/_generate_scripts.py`, mirroring `classification/step1_cv_harness/cv_config.py`'s `discover_combos()`.
- **`MAX_EPOCHS=250`, `EARLY_STOPPING_PATIENCE=7`** — user-specified, and (confirmed via exploration) these are the exact values classification's own live single-run trainer and current CV harness already use. Not a coincidence fought against; a convention matched.
- **`torch.optim.lr_scheduler.ReduceLROnPlateau(mode="min", factor=0.5, patience=3, min_lr=1e-6)`**, stepped on val_loss every epoch — mirrors `cv_trainer_engine.py`'s exact hyperparameters, with scheduler patience (3) kept low enough relative to early-stopping patience (7) that the scheduler gets to act before early stopping can fire (same ratio principle that source documents).
- **`BATCH_SIZE=32`**, independent constant local to `kfold_engine.py` — does not touch `dataset.py`'s `BATCH_SIZE=16`, which the original Optuna sweep scripts still use unchanged.
- **No backbone-freezing subtlety to replicate**: `classification/step1_cv_harness/cv_engine.py` has a documented `_mutable_state()` fix for BatchNorm buffers continuing to update under `model.train()` even when a backbone is frozen. Confirmed earlier this session that no segmentation model in this project freezes anything (`trainer_engine.py`'s optimizer is built from `model.parameters()` unfiltered) — so that fix doesn't apply here, correctly omitted rather than blindly copied.
- **One checkpoint per fold** (fp16, via `trainer_engine._half_state_dict()`, reused not duplicated) — 3 files/combo, not the 9 a repeated 3×3 would have needed.

## Files added

- **`Segmentation/scripts/dataset.py`** — additive: `AlignedConjunctivaSegmentationDataset.__init__` gained an optional `patient_ids: list[str] = None` param. When given, it overrides `split`-based filtering entirely (fold membership isn't a fixed named split). Omitted → behavior byte-identical to before (verified: `split="train"` alone still returns 143, matching the long-established count).
- **`Segmentation/scripts/train_pretrained_kfold/kfold_engine.py`** (new) — the shared K-fold engine. Imports and reuses `trainer_engine.train_one_epoch`/`evaluate`/`_half_state_dict`/`count_parameters`/`measure_inference_latency` and `segmentation_metrics.evaluate_final_test_set` unchanged; new logic is the fold splitting, the scheduler, per-fold checkpoint+test-eval, and cross-fold aggregation (mean/std of test Dice/IoU/Precision/Recall/HD95). Entry point: `run_kfold_study(model_name, build_model, tissue_type, image_size, learning_rate, weight_decay, loss_fn_name, n_folds=3)`.
- **`Segmentation/scripts/segmentation_plots.py`** — additive: `plot_kfold_mean_curve()` (mean ± std train/val loss and val Dice/IoU across all folds, epoch-aligned via a NaN-skipping pandas mean/std rather than padding stopped folds forward — this is what actually delivers "smooth loss curve," since averaging independent noisy runs is what smooths noise, a single run's curve can't) and `plot_fold_dice_distribution()` (per-fold test Dice bar chart, replacing the old loss-fn-comparison plot which no longer applies with one fixed loss function). New `generate_kfold_plots()` orchestrates these two plus the three existing test-set plot functions (`plot_test_set_summary`/`plot_test_set_by_country`/`plot_per_patient_distribution`), reused completely unchanged, fed pre-aggregated (pooled-across-folds) data. Net: **5 plots per combo**, not 6 — the original 2 separate training-curve plots (loss curve, Dice/IoU curve) consolidated into 1 combined 2-panel `kfold_mean_curve` image, a deliberate simplification, not a dropped metric.
- **`Segmentation/scripts/train_pretrained_kfold/_generate_scripts.py`** (new) — dynamically discovers the 12 completed combos by globbing `train_pretrained/output/segmentation_sweep_results*/logs/*_study_summary.json`, generates one `train_kfold_{model_name}.py` per combo.
- **12 generated entry-point scripts**, `Segmentation/scripts/train_pretrained_kfold/train_kfold_{model_name}.py`.
- **3 Kaggle notebooks**, `Segmentation/Kaggle-Notebook/segmentation-kfold-{base,mid,strong}.ipynb` — one per tier (4 combos each: that tier's CNN + Hybrid architecture, both tissue types), each self-contained (Setup/clone/dataset-path/pip-install/data-staging/sanity-check cells copied from the already-fixed tier-notebook pattern, `optuna` dropped from the pip-install list since this pipeline doesn't use it) plus 4 training cells and a Done section.

## Real bugs found and fixed during this build (verify-empirically, not just by inspection)

1. **Tissue-type suffix ambiguity in the generator's combo discovery.** `model_name.endswith("_palpebral")` matches `"..._forniceal_palpebral"` too (it's a real suffix of it), so checking `"palpebral"` before `"forniceal_palpebral"` in the candidate list silently produced a bogus `arch_key` (`"..._forniceal"`, not in the registry) for all 6 forniceal combos — caught immediately by actually running the generator (6 of 12 expected combos were silently skipped with a warning) rather than by reading the code. Fixed by checking candidates longest-suffix-first.
2. **nbformat cell-`id` length limit.** Cell IDs embedding the full `model_name` (e.g. `final-listing-cnn_mid_resnet101_deeplabv3plus_forniceal_palpebral`, 67 chars) exceeded nbformat's 64-char cap, caught by `nbformat.validate()` on 1 of the 12 notebooks. Fixed by using short, generic per-notebook-unique IDs instead (cell IDs only need to be unique within a file, not globally, so the model name was never actually needed in them).
3. **`cell["source"]` list-vs-string inconsistency** when copying cells from the real, Kaggle-executed tier notebook (some cells store `source` as a list of lines, not a single string, depending on how they were last saved) — caught by an `AttributeError` on the first generation attempt, fixed by normalizing to a joined string in the cell-cleaning helper.

## Estimated compute (worst-case, for the record — early stopping + the scheduler will likely reduce this in practice)

Derived from real measured per-epoch cost (EfficientNet-B1: ~90s/30 epochs at the old `batch=16` → ~3.0s/epoch), scaled by each architecture's measured inference-latency ratio:

| Architecture | Both tissue types, 3 folds, worst-case |
|---|---|
| EfficientNet-B1 | ~1.3h |
| CoAtNet-0 | ~1.0h |
| ResNet101+DeepLabV3+ | ~1.4h |
| CoAtNet-2 | ~2.0h |
| TransUNet | ~1.6h |
| ConvNeXt-Large | ~4.1h |
| **Total, all 12 combos** | **~11.4h worst-case** |

Every combo individually fits well within a single 12h Kaggle session. **Watch item, not yet confirmed either way:** `BATCH_SIZE=32` (up from 16) for ConvNeXt-Large (203M params, already the heaviest of the 12) could push closer to the T4's memory ceiling — no evidence yet, flagged for the first real run of that combo's notebook.
